Game PRD 3.0 Architecture Visual

A visual companion for the PRD 3.0 service architecture. The Markdown PRD remains the source of truth; this page shows the current runtime services, module boundaries, and data flow in one scan.

Services: 4 Docker runtime services Backend: Express modular monolith Realtime: WebSockets in backend runtime Durability: Database service + volume

Runtime Services

Service 1

Nginx Entrypoint / Reverse Proxy

Owns routing and proxy configuration. Browser traffic enters here before being forwarded to frontend or backend.

  • i. HTTP Route Config Area
  • ii. REST API Route Config Area
  • iii. WebSocket Upgrade Config Area
  • iv. TLS / Proxy Security Config Area
Does not own app pages, auth, gameplay rules, runtime match state, or database access.
Service 2

Next.js Frontend Service

Owns app pages, page rendering, non-game page composition, frontend client code, and the Excalibur Active Match presentation host.

  • i. App Shell Module
  • ii. Routing Module
  • iii. Page UI Modules
  • iv. REST Client Module
  • v. WebSocket Client Module
  • vi. Frontend State Module
  • vii. Localization Module
  • viii. Active Match Host Module

Excalibur Active Match Layer

  • Match Scene Module
  • Combatant View Module
  • HUD View Module
  • Question View Module
  • Effects Module
  • Overlay Module
  • Input Presentation Module
Builds non-game pages from static content or backend data; serves Active Match frontend code; does not own match-critical calculations or persistence.
Service 3

Express Backend Service / Backend Modular Monolith

Owns application authority: auth, profile, friends, matchmaking, live match state, questions, CPU behavior, results, REST APIs, and WebSockets.

  • i. Auth Module
  • ii. Player Profile Module
  • iii. Friends Management Module
  • iv. Stats / Leaderboard Module
  • v. Matchmaking Module
  • vi. Live Match Module
  • vii. Match Summary Module
  • viii. Question Generation Module
  • ix. CPU Opponent Module

x. Additional Backend Runtime Responsibilities

  • Backend Runtime Memory Temporary process state for queues, rooms, ready/reconnect timers, active match coordination, WebSocket sessions, and the Community Chat latest-50 buffer.
  • Community Chat Runtime Handler Validates chat messages, censors offensive language, stores only the latest 50 messages in memory, and broadcasts censored chat events.
  • Internal Module Handoffs Coordinates Matchmaking -> Live Match, Live Match -> Question Generation, Live Match -> CPU Opponent, and Live Match -> Match Summary.
  • REST API Groups Groups backend routes for Auth, Profile, Friends, Stats / Leaderboard, CPU Progress, and optional legal/localization resources.
  • Boundary And Data Ownership Notes Keeps runtime memory, database persistence, module ownership, and cross-module reads/writes separated.
One backend service/container. Modules are internal ownership groups, not microservices.
Service 4

Database Service

Runs the database engine and exposes the database connection to the Express backend. It does not run gameplay timers, active HP, chat buffers, or visual events.

Volume / Persistent Database Storage

Database Service reads/writes its data directory in this mounted volume so schemas, tables, indexes, and rows survive container restart/rebuild. Backend connects to the Database Service, not directly to this volume.

  • i. Users Schema / Persistence Area
  • ii. Player Profiles Schema / Persistence Area
  • iii. Friendships Schema / Persistence Area
  • iv. PvP Matches Schema / Persistence Area
  • v. CPU Progression Schema / Persistence Area
  • vi. Constraint / Index Area
Detailed table contracts live in Database Tables / Persistent Data Management.

2 Traffic Flows

One shared Nginx entrypoint routes traffic. It does not build pages or request backend data by itself. Non-game pages are composed by the Next.js frontend service using static content or REST data from Express. Game/realtime screens load frontend game code, then the browser runs Active Match Host and Excalibur while a WebSocket connection carries authoritative events to and from Express.

Non-Game Pages: Next.js Builds The Page

Use this path for Auth, Home, 1P/2P menus, Community, Profile, Leaderboard, Stats, Results, Privacy Policy, and Terms Of Service.

1. User / Browser User clicks navigation, submits a form, or opens a non-game page. Browser sends the page request to Nginx.
page request
2. Nginx Entrypoint Routes page and asset requests to the Next.js frontend service.
forward to frontend service
3. Next.js Frontend Service Chooses the page route and composes the page. Static pages, such as Privacy Policy and Terms Of Service, can return without backend data.
If the page needs backend data Next.js calls Express REST APIs for auth, profile, friends, stats, leaderboard, CPU progress, match summary, or other page data.
REST data request from Next.js to Express
4. Express Backend Service Owns the API/module logic and computes or validates the requested data. Uses Database Service only when durable data is needed.
database read/write when needed
5. Database Service + Volume Database Service reads/writes data in the mounted Volume. Express talks to Database Service, not directly to the Volume.
returned data continues to Express, then Next.js
6. Next.js Builds Response Next.js receives backend data and builds the populated non-game page. Next.js returns the completed page/assets through Nginx.
completed page response reaches browser
7. Browser Displays Page Browser presents the page built by Next.js.

Game / Realtime: Browser Runs Excalibur

Use this path for Active Match, Round Prep, PvP reconnect overlay, matchmaking updates, live gameplay, Community Chat, and realtime result/rematch events.

1. User / Browser User enters a game or realtime surface. Browser requests the page through Nginx.
page request
2. Nginx Entrypoint Routes the page/assets request to Next.js. Later, it proxies WebSocket upgrade traffic from the browser to Express.
load game frontend code
3. Next.js Frontend Service Serves Active Match Host, Excalibur scene code, page UI code, and frontend client code. Does not decide HP, damage, valid answers, winners, or persistence.
frontend code reaches browser
4. Browser Runs Active Match Host The browser executes a downloaded copy of frontend code that originally lives in the Next.js service. Active Match Host opens the realtime connection, handles local input, and coordinates the game screen.
mounts Excalibur presentation layer
5. Excalibur Renders Locally Excalibur runs in the browser as the visual/game presentation layer. It draws the active match scene, HUD, effects, overlays, and local input presentation.
WebSocket commands/events through Nginx
6. Express Backend Service Matchmaking, Live Match, Community Chat, and reconnect handlers own realtime state. Live Match is authoritative for timers, answer ordering, HP, damage, DEFEND, revenge, round results, and match results.
authoritative events reach browser through Nginx
7. Active Match Host Receives Events Backend events do not return through the Next.js server. The browser-loaded Active Match Host receives them from the WebSocket connection and prepares presentation updates.
passes presentation events to Excalibur
8. Excalibur Renders Events Excalibur renders HP changes, attacks, DEFEND, stun, prompts, overlays, and match transitions.
Current model: Next.js is the page-building mediator for non-game pages and results/data-backed surfaces. Browser-loaded Active Match Host is the game-screen controller/glue, and Excalibur is the game renderer. Express owns backend data, realtime handlers, and game truth. Database Service reads/writes the mounted Volume for durable page/result data; persistence is not part of the live rendering loop.
REST fits non-game data
  • Stable request/response work.
  • Non-game page data.
    • Auth.
    • Profile.
    • Friends.
    • Stats.
    • Leaderboard.
    • CPU progress.
    • Match summaries.
WebSocket fits realtime flow
  • Server-pushed updates that must arrive immediately.
    • Quick Match.
    • Room assignment.
    • Private invites.
    • Challenge / Ready.
    • Active Match.
    • Reconnect.
    • Rematch.
    • Community Chat.
Nginx only routes/proxies
  • Forwards page/assets traffic to Next.js.
  • Forwards REST/WebSocket traffic to Express.
  • Does not decide gameplay, compose pages, or request database data on its own.

Authority Rules

  • Backend owns gameplay truth. HP, damage, answer validity, server timestamps, round winners, match winners, and voids are backend-owned.
  • Frontend owns presentation. Next.js and Excalibur display authoritative state and send commands; they do not decide match-critical outcomes.
  • Database Service owns the database interface. The database container runs the database engine and exposes the connection used by the backend.
  • Volume owns physical durability. The mounted volume stores the underlying database files that hold schemas, tables, indexes, and rows.
  • Runtime memory is temporary. Queues, rooms, ready timers, active match coordination, WebSocket sessions, and latest-50 chat buffer live in backend process memory for MVP.
  • Additional backend runtime responsibilities are not a tenth module. They describe shared runtime memory, chat handler, handoffs, REST groups, and ownership boundaries.
